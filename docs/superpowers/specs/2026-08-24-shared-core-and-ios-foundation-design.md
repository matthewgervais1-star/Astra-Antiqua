# Shared Core and iOS Foundation — Design

**Date:** 2026-08-24
**Status:** Approved in conversation ("Ok so build it out") after the constraint review below.

## What this is

The foundation for an iPhone version of Astra Antiqua, built in the order that
survives every answer to the one unresolved question (Mac access), and that
stops the hand-sync drift instead of tripling it:

1. **Shared content JSON** (`shared/content/`) — generated from the canonical
   web data by a script, never hand-edited. This is the Phase 4 extraction that
   `docs/shared-content-model.md` already declares as the plan.
2. **C# domain core** (`dotnet/AstraAntiqua.Core`) — chart math and content
   access in a plain class library, buildable and testable on this Windows
   workstation with the stock .NET SDK. No MAUI workload required.
3. **Parity tests** — golden values generated by running the *web* logic, then
   asserted by the C# tests, so the port is proven equivalent rather than
   assumed.
4. **MAUI iOS head + CI** (`dotnet/AstraAntiqua.App` + GitHub Actions) —
   scaffolded and committed, built on a **macOS runner**, because Apple's build
   tools run only on macOS. This piece is explicitly *not verifiable* on this
   machine and is labeled as such.

## Constraints that shaped this (verified 2026-08-24)

- **iOS compilation and code-signing require macOS.** MAUI does not change
  this; Pair-to-Mac / a macOS CI runner is the architecture, not a workaround.
  Hot Restart (the one Mac-free path) is debug-only, ships a stock .NET icon,
  and is removed in VS 2026 — unusable for this product.
- **This machine has .NET SDK 8.0.423, no Visual Studio, no MAUI workload.**
  `net8.0-ios` is out of support; the app head targets **.NET 10 / MAUI 10 in
  CI**. The Core library multi-targets `netstandard2.0` so any head (MAUI 10
  today, anything later) can consume it.
- **App Store distribution additionally requires** the Apple Developer Program
  ($99/yr) and a signing identity. Out of scope here; the CI workflow builds
  unsigned until credentials exist.
- **The ephemeris ports cleanly:** `CosineKitty.AstronomyEngine` on NuGet
  (netstandard2.0) is the same upstream as web's npm package and Android's JAR.
- **The user chose:** keep the Kotlin Android app; the .NET surface is for iOS.
  The Core library is deliberately head-agnostic so that decision can change
  later without rework.

## Architecture

```
web/src/data/*.ts  ──(scripts/export-content.mjs)──▶  shared/content/*.json
web/src/lib/*.ts   ──(scripts/export-goldens.mjs)──▶  golden test fixtures
                                                          │
                                                          ▼
                                    dotnet/AstraAntiqua.Core (netstandard2.0)
                                      • Model: Culture, Planet, ZodiacSign, AspectKind
                                      • Astronomy: geocentric ephemeris, ascendant/MC
                                      • Charting: whole-sign houses, aspect detection
                                      • Content: loads shared JSON (embedded resources)
                                                          │
                                     dotnet/AstraAntiqua.Core.Tests (net8.0, xUnit)
                                                          │
                                     dotnet/AstraAntiqua.App (net10.0-ios, CI-built)
```

### 1. Shared content JSON (`shared/content/`)

Generated, committed, and regenerated by `cd web && npm run export:content`.
Web stays the source of truth; the JSON is the interchange format. Scope for
this iteration is the **chart-reading core** (not the full 27-file corpus):

| File | Source | Records |
|---|---|---|
| `cultures.json` | `cultures.ts` | 5 cultures, 10 planets, received set, labels, glyphs |
| `deities.json` | `deities.ts` | 50 (culture × planet), with epithet/note/contested |
| `planet-in-sign.json` | `planetInSign.ts` | 120 universal paragraphs |
| `houses.json` | `houses.ts` | 12 whole-sign houses |
| `zodiac-signs.json` | `zodiacSigns.ts` | 12 signs with element/modality/traits/dates |
| `aspect-rules.json` | `sampleChart.ts` | the one documented orb table (8/5/7/7/8) |
| `manifest.json` | generator | source commit, generation time, per-file counts |

The generator runs the TS modules directly under Node 24 type stripping, with
a small resolver hook for the `@/` path alias. It **fails loudly** if counts
don't match the expected shape (5 cultures, 10 planets, 50 deities, 120
paragraphs, 12+12, 5 rules) — the same completeness discipline as
`buildMatrix()` in `deities.ts`.

Android is *not* rewired to this JSON in this iteration; that is the existing
rollout plan's Phase 3 and stays there. This directory simply gives it (and
iOS) the thing to migrate onto.

### 2. C# Core (`dotnet/AstraAntiqua.Core`)

Plain class library, `netstandard2.0` (+ `net8.0` for modern consumers),
nullable enabled. Depends only on `CosineKitty.AstronomyEngine` and
`System.Text.Json`. Content JSON is embedded as resources so the library is
self-contained for any head.

- **Model** — `Culture` (5), `Planet` (10, with `IsReceived`), `ZodiacSign`
  (12), `AspectKind` (5), `Deity`, `HouseMeaning`, `ZodiacSignInfo`,
  `NatalChart`, `Placement`, `Aspect`.
- **Astronomy** — `Ephemeris.EclipticLongitude(planet, utc)`: **geocentric**
  ecliptic longitude (Sun via `Astronomy.SunPosition`, Moon via
  `Astronomy.EclipticGeoMoon`, planets via `GeoVector(aberration) → Ecliptic`).
  This mirrors `web/src/lib/ephemeris.ts` exactly. The library's
  `EclipticLongitude()` helper is heliocentric and is **never called** — the
  same landmine Android hit and documented in `AstronomyEngine.kt:13-20`.
  `Ascendant.Compute(utc, lat, lon)`: Meeus ch. 13 formula with mean obliquity
  23.4392911°, ported from `web/src/lib/ascendant.ts`.
- **Charting** — `ZodiacMath.LongitudeToSign` (30° blocks from 0° Aries,
  **throws** on non-finite input, matching web), `Houses.WholeSign(ascSign)`,
  `Aspects.Detect(chart)` reading the aspect-rules JSON, normalized separation,
  **break on first match** (web behavior; the Android double-count bug is not
  reproduced).
- **Content** — `ContentStore`: loads embedded JSON once, exposes
  `GetDeity(culture, planet)`, `GetPlacementText(planet, sign)`,
  `GetHouse(n)`, `GetSignInfo(sign)`; static invariant check on load.

Out of scope for Core in this iteration (recorded, not forgotten):
birth-input → UTC resolution (needs NodaTime + a tz-lookup equivalent; head
concern), transits/synastry/forecast/week/season/year composition, the
FNV-1a-seeded permissions PRNG (needs exact JS 32-bit wraparound semantics —
port it only with a bit-level parity test, later), persistence, auth.

> **Note, 2026-09-29.** Section 1 says Android is not rewired to this JSON in
> this iteration. It was rewired the next day, 2026-08-25: `13f428d` wires
> `shared/content` in as a build-time asset with a cached placement loader, and
> `9922e1c` tests the loader, deity parity and a composed golden.

### 3. Parity tests (`dotnet/AstraAntiqua.Core.Tests`)

xUnit on net8.0, runnable here with `dotnet test`.

- **Golden chart test** — `web/scripts/export-goldens.mjs` runs web's own
  `computeChart` + `computeAscendant` + whole-sign + aspect detection for
  fixed instants/locations and writes `goldens.json`. C# asserts longitudes
  within **0.001°** and exact sign/house/aspect agreement. Cross-language
  parity of Astronomy Engine is designed-in upstream; the tolerance covers
  minor version skew between the npm and NuGet builds.
- **Completeness tests** — every (culture × planet) deity, every (planet ×
  sign) paragraph, 12 houses, 12 signs, the exact orb table.
- **Behavioral tests** — sign wraparound, whole-sign houses from a Pisces
  ascendant, aspect break-on-first-match at a boundary separation,
  non-finite longitude throws.

### 4. MAUI head + CI (`dotnet/AstraAntiqua.App`, `.github/workflows/ios.yml`)

Minimal MAUI 10 project targeting `net10.0-ios` only, referencing Core:
`MauiProgram`, one page proving the pipeline (today's chart for a fixed
location rendered as text from Core + ContentStore). **Cannot be built or run
on this workstation** — no MAUI workload, and iOS builds need macOS. The CI
workflow (macOS runner: install .NET 10, `dotnet workload install maui`,
build unsigned for simulator) is the verification path; it runs when pushed
to GitHub. Committed clearly labeled as CI-verified only.

The real iOS UI (the Instrument-in-the-Temple identity, culture grounds,
navigation) is a separate design exercise against
`docs/design/handoff/` — deliberately not started here.

## Error handling

- Generator: throws on any count mismatch or missing field; never writes
  partial output (writes to temp, renames on success).
- Core: `ContentStore` throws on load if any invariant fails (fail at startup,
  not at lookup); `LongitudeToSign` throws on non-finite input; ephemeris
  exceptions propagate (the head decides how to degrade — Android Phase 4's
  Pluto range guard lives at the head/use-case level, not in Core).

## Testing

`cd web && npm run export:content && npm run export:goldens` then
`cd dotnet && dotnet test` — all green locally. `npm run gates` (web's
existing checks) stays green; web runtime behavior is untouched (scripts
only). CI workflow is the MAUI head's gate.
